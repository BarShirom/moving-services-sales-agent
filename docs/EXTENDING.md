# Extending the application

Start with the [engineering guide](ENGINEERING_GUIDE.md) and run the offline baseline before changing behavior. The model proposes facts; requirements select missing information; deterministic code calculates recommendations; the owner approves the final quote. The server remains authoritative for lifecycle state and available actions. Acceptance records commercial agreement awaiting manual coordination.

## Architecture map

| Boundary | Main modules | Ownership |
| --- | --- | --- |
| Browser session | `client/src/useDemoSession.ts`, `api.ts`, `App.tsx` | The hook owns customer/owner snapshots, draft, requests, recovery, errors and distinct AI/request cooldowns. The API helper owns HTTP details. App owns DOM focus/scroll and view composition. |
| Presentation and owner input | `leadPresentation.ts`, `displayFormatting.ts`, `ownerPricingPresentation.ts`, `OwnerView.tsx`, `OwnerFinalizationForm.tsx` | Exhaustive lifecycle presentation and shared formatting; finalization fields/acknowledgements stay local to the owner form and never establish server approval. |
| Facts and recognized items | `server/src/domain/lead.ts`, `createMoveItem.ts`, `itemTypes.ts`, `domain/extraction/` | Explicit unknowns, shared known item identifiers and conservative patches. Recognition does not establish pricing support. |
| Provider boundary | `server/src/integrations/openai/{context,prompt,schema,convertExtraction,extractMessageWithAI}.ts` | Bounded input, structured response validation and conversion into fact patches. No model-owned prices, approvals or lifecycle updates. |
| Collection and conversation | `server/src/domain/requirements/{itemRequirementProfiles,evaluateRequirements,nextQuestion}.ts`, `domain/conversation/` | Item collection policy, relevant questions, contextual replies and deterministic quote acceptance. |
| Deterministic pricing | `server/src/domain/pricing/{itemPricingPolicy,buildPricingInput,pricingRules,calculatePrice,evaluateLeadPricing}.ts` | Separate transport/service/load policies, detached pricing input, versioned tariffs, arithmetic and omissions. |
| Workflow and HTTP session | `server/src/demo/{ownerWorkflow,router,sessions,protection}.ts`, `domain/quote/{types,quoteScope}.ts` | Lead revisions, owner actions, immutable quote scope/version, expiry/busy guards and process-local quotas. |
| Durable AI admission | `server/src/safety/aiWindow.ts` | Operator permit, fixed expiry, cumulative reservations and allowlisted diagnostics, independent of temporary business sessions. |

Express app creation stays in `server/src/app.ts`; `server.ts` owns environment loading, listening and shutdown. The public API and the existing deployed security/accounting configuration are compatibility boundaries.

## Item identity limitation

Known item types are identifiers for categories, not stable item identities. `MoveItem.type` remains a generic string or `null`; sharing the recognized identifier list does not narrow every historical or owner-supplied item to that list. Item-index references in requirements describe the current array position only.

`mergeExtraction` matches a patch by type. With no match it creates an item; with exactly one match it updates that entry. If multiple existing entries share the type, it returns the patch in `unappliedItems` instead of guessing. Repeated same-type mentions may therefore update one aggregate entry, and two refrigerators with different sizes or access needs cannot reliably be targeted independently. Quantity is not an item ID. Additive updates, removal and clearing also have existing limits.

Keep this conservative behavior in tests. Stable IDs would cross extraction targeting, merge rules, requirement references, pricing fingerprints, quote scopes, API compatibility and migration. They remain a separate follow-up, together with durable business storage and authenticated roles.

## Working safely across boundaries

Use detached facts for pricing; never write a pricing-only quantity assumption back into the Lead. Acknowledging a missing photo changes an owner decision, not the factual photo status. Service support does not establish transport support, and a supported subtotal does not price omitted furniture/access work.

Session recovery cannot restore lost business records from the AI ledger. Replacing the backend must preserve that ledger, its fixed expiry and spent reservations through the existing operator configuration. Do not introduce retries, provider fallbacks, new credentials, deployment changes or automatic mutations as incidental parts of a maintainability change.

For browser verification, exercise customer collection, owner finalization, explicit acceptance and recovery with the guarded offline fixture or injected responses. Check desktop and narrow viewports. Record interaction/overflow measurements separately from screenshots actually captured and inspected; do not claim visual verification from interactions alone. Keep dated release reports unchanged and record new results in a new report.
